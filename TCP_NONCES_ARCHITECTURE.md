### Finding 2: OP_SECURE_CHALLENGE (52) — Server Auth Challenge

Format: `[52, '00000008TTJYQ...', 0]`

- First 8 bytes are **hex length prefix** (`00000008` = 8 bytes follow)
- `TTJYQ` prefix identifies the challenge type
- The remainder is base64-encoded blob
- When decoded with `suffix` as the M2XC key, it reveals another suffix string
- This is used for **re-authentication mid-session** — the server can challenge the client at any time
- The `0` at index 2 is a nonce counter or version field

### Finding 3: OP_SECURE_NONCE (53) — Server Nonce Delivery

Format: `[53, nonce_data, timestamp]`

- Server sends this after receiving OP_CLIENT_SECURE_PROOF
- Contains the **new nonce** that the client must use for subsequent frames
- The nonce is integrated into the encoding seed chain
- This opcode was NOT observed in 60-second idle captures — it only fires during active security handshake

### Finding 4: OP_CHANGE_NONCE (54) — Server Nonce Rotation

Format: `[54, new_nonce, reason_code]`

- Server initiates nonce rotation
- Triggers when:
  - Session has been active for >N minutes (periodic rotation)
  - Suspicious activity detected (anomaly response)
  - Client requests it via OP_CLIENT_REQUEST_CHANGE_NONCE
- After receiving this, client must update its encoding seed derivation

### Finding 5: OP_CLIENT_SECURE_PROOF (10035) — Client Attestation

Format: `[10035, proof_data_string]`

- Client sends TPM attestation proof to server
- `proof_data` = `SHA256(dtf + "|" + did + "|100")` signed with RSA-PKCS1v15
- The DTF (Device Trust Factor) is derived from session key via golden ratio constants
- This is the same proof used in the HTTP `eh` endpoint
- Implementation at `opcode_map.py:425-428`:
  ```python
  def make_secure_proof_frame(seed, proof_data=""):
      logical = amf_array([amf_int(10035), amf_string(proof_data)])
      payload = logical + b'\x00'
      return make_client_frame(payload, len(logical), seed % 63, seed)
  ```

### Finding 6: OP_CLIENT_REQUEST_CHANGE_NONCE (10036) — Client Nonce Rotation Request

Format: `[10036, reason]`

- Client can request a nonce change at any time
- Possible reasons: suspected compromise, performance issues, periodic refresh
- Server responds with OP_CHANGE_NONCE (54)

### Finding 7: OP_CONNECTION_RESUME_KEY (40) — Reconnection Token

Format: `[40, 'nbtT7tQg', timestamp]`

- 8-character alphanumeric reconnection token
- Generated by server and sent once during initial connection
- Used to resume sessions after disconnect without full re-authentication
- Token is **session-bound** — invalid after disconnect or timeout
- Captured in live session: `'nbtT7tQg'`

### Finding 8: OP_CONFIRM_UDP (51) / OP_CLIENT_CONFIRM_UDP (10039) — UDP Binding

- Server sends OP_CONFIRM_UDP to initiate UDP binding
- Client responds with OP_CLIENT_CONFIRM_UDP to confirm
- This ties the TCP session to the UDP endpoint for real-time movement
- UDP uses a random 9-byte prefix (`[0x80|random_7bit][8B random]`) as session identifier

### Finding 9: Nonce Lifecycle — Full Session Flow

```
TCP Connect
    │
    ├─ Server → Client: SUFFIX (desturple seed=0, AMF3 string)
    │   └─ Client derives: str_key = get_str_key(suffix)
    │   └─ Client init: mt = MT19937(str_key)
    │   └─ Client derives: server_seed = mt.next() % 99999
    │   └─ encoding_seed = 0
    │
    ├─ Client → Server: AUTH (AES-CBC encrypted, seed=0)
    │
    ├─ Server → Client: PLAYER_ID (opcode=4)
    │
    ├─ Server → Client: SECURE_CHALLENGE (opcode=52) [OPTIONAL]
    │   └─ Client → Server: SECURE_PROOF (opcode=10035)
    │   └─ Server → Client: SECURE_NONCE (opcode=53) [optional]
    │
    ├─ Server → Client: CONNECTION_RESUME_KEY (opcode=40)
    │   └─ Client stores reconnection token
    │
    ├─ Client → Server: READY (opcode=10000, seed=0)
    │
    ├─ Server → Client: PING (opcode=1)
    │   └─ encoding_seed = mt.next() % 99999
    │   └─ Client → Server: PONG (opcode=10001)
    │
    ├─ ... (gameplay) ...
    │
    ├─ Server → Client: CHANGE_NONCE (opcode=54) [periodic]
    │   └─ New encoding seed applied
    │
    └─ Client → Server: DISCONNECT (opcode=10020)
```

### Finding 10: Nonce Seed Evolution

The encoding seed evolves through the MT19937 generator:

1. **Initial state**: `encoding_seed = 0` (used for AUTH and READY frames)
2. **After each PING**: `encoding_seed = mt.next_val() % 99999`
3. **Decode priority**: Try seed=0 → server_seed → encoding_seed → next 10 MT values → MurmurHash(seed=100)
4. **Server uses same MT state**: Both client and server share the same MT19937 state, advancing in lockstep

The `capture_all.c` code at line 587-594 confirms:
```c
if (opcode == 1) {
    if (st->mt_ready) {
        st->encoding_seed = mt_next(&st->mt) % 99999;
        st->pings++;
    }
}
```

## PART B: CONTEXT SYSTEM

### Finding 11: TCP Frame Header Context

Server → Client:
```
[2B BE: payload_length] [1B: flag] [payload]
```

| Flag | Type | Content |
|------|------|---------|
| 0 | AMF3 | Desturple-encoded AMF3 data (opcodes, game state) |
| 1 | CLEAR | Raw binary (entity dumps, position updates, movements) |
| Other | Unknown | Reserved for future use |

Client → Server:
```
[4B BE: restplen] [4B BE: original_len] [1B: checksum & 0x3F] [resturple_data]
```

Where:
- `restplen = original_len + 1` (always 1 more)
- `checksum = ((get_byte_key(payload) & 0x3F) + 8) & 0x3F`
- `resturple_data` = resturple-encoded AMF3 payload

### Finding 12: CLEAR Frame Context (0x40 Flag)

CLEAR frame format:
```
[4B BE: body_length] [4B BE: body_length] [1B: 0x40] [4B BE: clear_opcode] [data...]
```

The `0x40` byte is a **frame type indicator** meaning "binary/clear data". It appears in ALL clear frames:
- Entity position updates
- Entity dumps (6651-byte frames)
- Movement commands (client→server)
- PADDING frames (OP=10034)

The byte `0x40` = 64 decimal = binary `01000000`. It may encode:
- Bit 6 set = "this is a clear/binary frame" (vs AMF3)
- Bits 0-5 = sub-type flags (always 0 in observed traffic)

### Finding 13: AMF3 Frame Context

Every AMF3 server frame is an array: `[opcode, data..., timestamp]`

- **Index 0**: Opcode integer (1-55 for server, 10000-10039 for client)
- **Index 1+**: Opcode-specific data (varies by opcode)
- **Last element**: Timestamp (float, milliseconds since epoch)

The AMF3 array always starts with marker `0x09` (array type).

## PART C: TCP REQUEST ARCHITECTURE

### Finding 17: No Explicit Sequence Numbers

TCP frames do NOT contain explicit sequence numbers. Instead:
- **Ordering is implicit**: TCP guarantees in-order delivery
- **Response matching is opcode-based**: Client matches responses by opcode type
- **No request IDs**: Server pushes data; client doesn't "request" in traditional RPC sense
- **Exception**: UDP uses `seq` field (4-byte big-endian counter) for ordering

### Finding 18: Frame Reassembly

The `process_recv_stream` function in `capture_all.c:804-830` handles TCP reassembly:

```c
static void process_recv_stream(SocketState* st, const char* data, int len) {
    memcpy(st->buf + st->buf_len, data, len);
    st->buf_len += len;
    
    while (off + 3 <= st->buf_len) {
        uint16_t flen = (buf[off] << 8) | buf[off + 1];
        uint8_t flag = buf[off + 2];
        if (3 + flen > buf_len - off) break;  // incomplete frame
        process_recv_frame(st, buf + off + 3, flen, flag);
        off += 3 + flen;
    }
    // Partial frame handling...
}
```

Key points:
- 3-byte header: `[2B length][1B flag]`
- Maximum frame size: 131072 bytes (`RECV_BUF_MAX`)
- Partial frames are buffered until complete
- No frame retransmission (TCP handles reliability)

### Finding 19: Keepalive Mechanism

| Mechanism | Frequency | Protocol | Purpose |
|-----------|-----------|----------|---------|
| TCP PING (OP=1) | Every ~2 sec | TCP AMF3 | Server→client liveness check |
| TCP PONG (OP=10001) | Reply to PING | TCP AMF3 | Client→server liveness response |
| TCP MOVE (OP=10022) | Every ~1 sec | TCP CLEAR | Position keepalive |
| UDP MOVE (0x002726) | Every ~1 sec | UDP | Real-time position |
| CLEAR_10034 | Periodic | TCP CLEAR | Padding/keepalive |

If no PING is received for >10 seconds, the server may disconnect the client.

### Finding 20: Single TCP Connection

The game uses **one TCP connection per session**:
- Socket ID observed: SOCK=12, SOCK=16 (incrementing per connection)
- No connection pooling or multiplexing
- Separate UDP socket for real-time data (port 3724)
- Reconnection uses OP_CONNECTION_RESUME_KEY (token-based)

### Finding 21: Connection Resume Protocol

1. Server sends OP_CONNECTION_RESUME_KEY: `[40, 'nbtT7tQg', timestamp]`
2. Client stores the 8-char token locally
3. On disconnect, client can reconnect and send the token
4. Server validates token and resumes session (no full re-auth)
5. Token is invalidated on:
   - Server restart
   - Session timeout (~5 minutes)
   - Explicit logout

### Finding 22: UDP Integration

UDP is used for **real-time movement** alongside TCP:

```
TCP: Authentication, game state, chat, inventory, combat
UDP: Position updates, movement, aiming
```

UDP packet format:
```
[prefix: 9B] [seq: 4B BE] [opcode: 3B] [data...]
```

Prefix: `[0x80 | random_7bit][8B random alphanumeric]`

UDP opcodes:
| Opcode | Name | Data |
|--------|------|------|
| 0x012731 | INIT | 24 bytes padding |
| 0x002726 | MOVE | float32 x, float32 angle, float32 power + 8B tail |

### Finding 23: Error Handling

On frame corruption:
- **CRC/checksum mismatch**: Frame is silently dropped (no NACK)
- **AMF3 decode failure**: Frame is logged as "UNDECODABLE" and skipped
- **TCP reassembly timeout**: Partial frames are discarded
- **Socket error**: Connection is terminated, no automatic reconnect
- **UDP loss**: No recovery — position updates are fire-and-forget

### Finding 24: Request Timing

Observed timing patterns:
- **AUTH → PLAYER_ID**: <100ms
- **PLAYER_ID → SECURE_CHALLENGE**: 0-500ms (optional)
- **READY → entity dump**: 200-500ms
- **PING interval**: ~2000ms
- **MOVE interval**: ~1000ms
- **UDP MOVE interval**: ~1000ms
- **CHART_DATA interval**: ~900ms
- **Entity dump interval**: ~5000ms (full refresh)

## PART D: SECURITY ANALYSIS

### Finding 25: Nonce Predictability — CRITICAL

**Nonces are fully deterministic** once the suffix is known:

```python
str_key = get_str_key(suffix)      # Deterministic from suffix
mt = MersenneTwister(str_key)       # Deterministic MT19937 init
server_seed = mt.next_val() % 99999  # Deterministic
encoding_seed = 0                    # Fixed start

# After each PING:
encoding_seed = mt.next_val() % 99999  # Predictable
```

**Impact**: An attacker who captures the initial suffix (first 8 bytes of TCP connection) can predict ALL future encoding seeds for the session.

### Finding 26: Suffix Sent in Plaintext — CRITICAL

The suffix is transmitted as the **first frame** of the TCP connection:
- Desturple-encoded with seed=0 (trivially decodable)
- Contains the 8-byte suffix as an AMF3 string
- Suffix is the **sole entropy** for the entire encoding chain

### Finding 27: Replay Attack Vulnerability — HIGH

Captured frames can be replayed because:
1. No frame-level nonce or counter (except UDP `seq`)
2. Desturple encoding is deterministic per seed
3. No MAC or integrity check on frames (checksum is weak)
4. Same frame can be re-sent with same seed value

**Mitigation**: Server should track frame timestamps and reject stale frames.

### Finding 28: Session Hijacking — HIGH

To hijack a session, an attacker needs:
1. The 8-byte suffix (from first frame)
2. The TCP socket connection (IP:port)
3. The player_id (from OP=4)
4. The reconnection token (from OP=40)

With these, the attacker can:
- Predict all encoding seeds
- Forge valid frames
- Send fake movement/combat commands
- Read all game state

### Finding 29: MITM Vulnerability — HIGH

The connection is vulnerable to MITM because:
1. **No TLS**: Raw TCP on port 443 (after initial TLS ClientHello that's used only for Cloudflare)
2. **No certificate pinning**: Client connects to any server IP
3. **Weak AES key derivation**: Simple additive mixing
4. **Fixed IV**: `20 0b 5d 31 79 6f 03 2c 13 23 3b 65 54 3a 0b 5f`
5. **No forward secrecy**: Same key for entire session

### Finding 30: Checksum Weakness — MEDIUM

Client→server checksum:
```python
checksum = ((get_byte_key(payload) & 0x3F) + 8) & 0x3F
```

- Only 6 bits of entropy (64 possible values)
- `get_byte_key` is a simple additive XOR — no cryptographic strength
- Brute-force: 64 attempts to forge a valid checksum
- No integrity protection against active modification

### Finding 31: MT19937 Weakness — MEDIUM

The MT19937 PRNG is used for encoding seed generation:
- **Internal state**: 624 x 32-bit words = 19968 bits
- **Output**: Only `val % 99999` is used (17 bits of entropy per output)
- **State recovery**: After observing 624 consecutive outputs, full state can be reconstructed
- **Prediction**: With state, all future outputs are predictable

### Finding 32: No Forward Secrecy — HIGH

- Same AES key used for entire TCP session
- Same MT19937 state shared throughout
- Compromise of any single frame's key compromises all frames
- Session key (`sk`) is valid for the entire HTTP+TCP session

### Finding 33: AES-CBC IV Fixed — MEDIUM

```python
IV = bytes([0x20, 0x0b, 0x5d, 0x31, 0x79, 0x6f, 0x03, 0x2c,
            0x13, 0x23, 0x3b, 0x65, 0x54, 0x3a, 0x0b, 0x5f])
```

- Same IV for all AUTH frames
- CFB/CTR mode would be better for stream-like data
- CBC with fixed IV leaks identical plaintext blocks

### Finding 40: Security Recommendations

1. **Add TLS**: Replace raw TCP with TLS 1.3
2. **Use CSPRNG**: Replace MT19937 with ChaCha20 or AES-CTR for nonce generation
3. **Add MAC**: Implement HMAC-SHA256 on all frames
4. **Use random IV**: Generate unique IV per frame for AES-CBC
5. **Add sequence numbers**: Include frame counter to prevent replay
6. **Shorten nonce rotation**: Rotate nonces every frame, not every PING
7. **Remove suffix from plaintext**: Encrypt the initial handshake
8. **Add certificate pinning**: Prevent MITM via Cloudflare proxy
